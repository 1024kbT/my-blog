# 产品实战：从点子到第一个 AI 产品 Demo

学习路线图解决的是“学什么”，产品实战解决的是“怎么做出第一个像样的东西”。很多人卡在这里，不是不会调用模型，而是不知道该怎么把一个想法压缩成最小可交付产品。

## 一、先别急着写代码，先把问题说清楚

一个 AI 产品点子如果说不清“谁在用、什么时候用、为什么不用原方法”，大概率会做成一个看起来热闹、实际没人回来的 Demo。

我通常会先写清四件事：

1. **用户是谁**：学生、运营、研发、内容创作者，角色不同，需求完全不同。
2. **任务是什么**：总结、改写、问答、分类、搜索、结构化输出。
3. **AI 的价值在哪里**：是省时间、提升质量，还是让原本做不到的事变得可行。
4. **最小成功标准是什么**：用户愿意连续用三次，还是只要看得懂一次结果。

## 二、最适合做第一批 Demo 的产品类型

如果是做练手项目，我会优先选这几类：

| 类型 | 为什么适合练手 | 容易补的能力 |
| --- | --- | --- |
| 文本摘要 | 输入输出清晰，容易衡量 | Prompt、结果卡片、加载态 |
| AI 改写 | 容易做多版本输出 | 输出格式、交互细节 |
| 文档问答 | 很快能接近真实业务 | 上下文、检索、历史记录 |
| 写作助手 | 用户价值直观 | 多轮、模板、结果复用 |

这几类的共同点是：足够小，但已经能覆盖 AI 产品的核心骨架。

## 三、把需求压缩成 MVP

最危险的事情就是第一版就想做：

- 多模型切换
- 多端同步
- 权限系统
- 工作流编排
- 复杂知识库

更稳的做法是先压成 MVP。我通常会用这个判断模板：

### 必须有

- 一个清晰输入框
- 一条稳定请求链路
- 一个可理解的结果区域
- 错误提示和重试

### 可以后补

- 历史记录
- 参数面板
- 输出复制、导出
- 多模板预设

### 暂时不要做

- 权限体系
- 多租户
- 复杂角色分工
- 多步骤工作流引擎

## 四、Prompt 不是“最后调一下”，而是产品设计的一部分

AI 产品里，Prompt 不只是技术细节，它本身就是体验的一部分。

我更推荐把 Prompt 看成一个四层结构：

1. 角色定义
2. 任务目标
3. 输入上下文
4. 输出约束

比如“帮我总结文章”这种需求，如果只写一句话，体验会非常飘；但如果能明确：

- 输出要分 3 点
- 每点不超过 60 字
- 语气偏客观
- 保留原文关键结论

结果稳定性会好很多。

## 五、页面设计里最容易被忽略的体验

一个能演示的 AI 产品，不只是“出来结果了”，还要让人不慌。

这几个状态特别关键：

### 1. 空态

用户第一次进来时，不该只看到一个空白输入框。最好给：

- 示例问题
- 推荐输入格式
- 预期输出说明

### 2. 加载态

不能只有转圈。最好告诉用户：

- 正在处理什么
- 可能需要多久
- 是否可以继续编辑

### 3. 失败态

不要只写“请求失败”。更像产品的写法应该是：

- 失败原因倾向
- 是否建议重试
- 是否建议缩短输入
- 是否建议切换模板

## 六、一个最小实战流程

如果让我从 0 到 1 做一个 AI Demo，我会按这个顺序：

1. 选一个单一任务场景
2. 写一版 Prompt 模板
3. 先用最小页面跑通请求
4. 补空态、加载态、失败态
5. 根据结果再调 Prompt
6. 最后才补历史记录和细节功能

这个顺序很重要。先把链路跑通，再做体验，不要反过来。

## 七、怎么判断它已经不是“作业”，而是“产品雏形”

我会看三件事：

- 别人第一次打开，不需要我站旁边解释也能用
- 连续试 3 次，结果体验基本稳定
- 即使失败，用户也知道下一步怎么办

只要做到这三点，这个 Demo 就已经不是玩具了。
